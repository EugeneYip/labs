## The bar (36 live experiments)

A candidate normally needs several of these, not one: a clearly identifiable role or user; a concrete workflow; real recurrence or stakes; measurable time or attention saved; meaningful error reduction; an important document, calculation, schedule, record, or decision produced; an official process or rule creating the work; a real privacy or local-processing advantage; a confirmed weakness in current alternatives; a task still done with spreadsheets, paper, email, templates, PowerPoint, or ad-hoc scripts; a browser-native interaction substantially better than the incumbent workflow; offline or accountless use that materially matters. Novelty alone is a reject.

- **Recent yield** (Batch 08: four; 09: two; 10: one) means the obvious browser-local opportunities are largely taken. Change the search strategy, not the gate.
- **Workflow depth over formula depth:** prefer import → reconcile → inspect → decide → export over "enter three numbers, get one". A simple calculation qualifies only with unusually strong incumbent evidence and stakes.
- **Don't overproduce rule calculators** (after #034 and #036): a rule-created job counts only when the workflow itself is substantial. Simple eligibility checks, lookup tables, yes/no compliance tools, and fast-moving legal guidance are usually rejected.

## Discovery: workflow first

Start from evidence of real work, not product categories: procedural manuals; professional and volunteer handbooks; association guidance; government forms; regulator guidance; certification procedures; competition rules; inspection forms; downloadable spreadsheet templates; printable worksheets; forum threads describing manual reconciliation; vendor feature requests, especially declined ones; official worked examples; workflows where people rebuild the same spreadsheet; jobs needing several tools to finish one small task. The question is what this person repeatedly has to produce, check, reconcile, allocate, transform, or calculate.

**Staged screening,** so weak ideas die cheaply:
- **Stage A, cheap kill:** is the audience real and specific; is the job substantial; does an obvious free tool already do it; does the useful version need a backend, account, or API? If weak, REJECT at once.
- **Stage B, opportunity check:** the actual workflow; recurrence and stakes; the strongest incumbent; the manual alternative; the Labs wedge; technical feasibility.
- **Stage C, full gate:** only the strongest few.

**Full BUILD gate** (a candidate stays unnumbered until all are answered): A audience (who does the job); B trigger (what starts it); C input (what they have before: spreadsheet, paper form, measurements, rules, schedule, export, list, drawing, transcript, scorecards); D output (the artifact or decision that must exist after); E frequency and stakes (how often; what happens if wrong or slow); F current workflow; G strongest incumbent, free ones included, never weakened; H the Labs wedge (why Labs is materially preferable); I technical fit within static, browser-local limits; J falsification (the strongest reason not to build, actively investigated; BUILD only if the thesis survives).

**Outcomes:** **REJECT** (the evidence fails; the deciding reason recorded; no number). **HOLD**, sparingly, only when one specific missing fact could change the result; it never blocks the batch, and if settling it needs the owner, a person, a new permission, a download not already allowed, or an account, it's parked. **BUILD** only when the evidence clearly clears the gate; then the next number (#037 first, in order, at most #041). Once implementation starts under a number, the number is permanent. Old HOLDs are reopened only if new autonomous evidence can settle them; the nest visit planner and the other owner-blocked ideas stay parked.

**Rule-based candidates:** read the primary rule itself where accessible (guidance explains, it doesn't replace); record effective dates; refuse outdated periods explicitly; expose every interpretation choice; no professional advice; record what future change would need maintenance. **Volatility gate:** reject or HOLD when implementation dates are unsettled, local authorities differ, several bodies changed the rules this year, the source is a draft, or correctness needs ongoing legal interpretation.

**Search budget:** before any thread, grep the records (`CANDIDATES.md` and `research/` in Batches 07–11, the earlier factory-state pools); search broad first; once a primary source is known, read it instead of searching again; keep the allowance for deciding uncertainties. Threads get one bounded purpose and write findings to `research/` as they go; a thread cut off by a limit is closed on its notes and relaunched only if the expected value stays high, never twice for a marginal lane. The main session owns decisions and checks every deciding claim itself.

## Per-experiment sequence

research → gate → number → `wip/<number>-<slug>` → pre-build risk review → implementation → independent correctness → browser QA → adversarial audit → fixes → shipping gate → one squashed commit on `main` → push → deploy → production verification → record → next discovery. One numbered experiment at a time; research may run alongside. Checkpoint verified milestones on the `wip/` branch (never pushed); keep this file's "Now", the factory state's "Now", and the dossier current, so git and the repository alone are enough to resume.

- **Pre-build risk review** (what applies): malformed input; ambiguous dates and numbers; locale; Unicode; duplicates; overlapping exports; huge input; stale UI state; fast typing; several tabs; storage failure; print and export; incomplete data; arithmetic precision; outside-rule changes; privacy claims; inaccessible workflows. It designs the tests.
- **Independent correctness:** never the production code alone: brute force, exhaustive small cases, randomized and property tests, invariants, an independent Python implementation, a separate algorithm, official examples recomputed (Batch 10 found official worked totals wrong), published reference results, independently generated fixtures, genuine exported files.
- **Real formats:** documented vendor layouts where they exist; real files from the software where already accessible; documented versus inferred formats said plainly; encodings and locales; malformed, overlapping, missing-column, and near-miss formats. Readers refuse uncertain data rather than guess.
- **Near the public limits:** if the page accepts N, test near N; no row, character, file-size, or record caps that QA never approaches; check stack limits, argument spreading, recursion, regex pathologies, quadratic work, huge DOMs, memory growth, lock-ups.
- **Fast users** (Comp Desk, Holiday Pay): fast paste and typing, Enter immediately, repeated keys, fields changed before the last render settles, background tabs, focus after controls appear or disappear. Not only slow automation.
- **Accessibility:** keyboard workflow, focus, accessible names, meaningful announcements, 200% text, phone, desktop, light and dark, reduced motion where it applies, print legibility, a manageable Tab count (and a keyboard strategy beyond Tab when there are dozens or hundreds of rows).
- **Browsers:** Chromium (Brave) and WebKit required; Firefox parked, never blocking.
- **Offline and local claims:** verify them; inspect network behaviour; state what is stored, what isn't, and anything sent out; no absolute privacy claims beyond the implementation.
- **Adversarial audit before any public push:** correctness defects, misleading wording, accessibility failures, data loss, parser ambiguity, performance cliffs, rule misunderstandings, false confidence. Suggestions aren't defects automatically: verify each finding.

**Shipping gate.** Product: the core job complete; no known material correctness defect; no silent data loss; invalid input safe; limitations visible; wording honest. Correctness: independent verification; realistic boundary tests; audit findings resolved. UI and browsers: Chromium, WebKit, desktop, phone, light, dark, keyboard, accessibility, console, print, export, and import where relevant. Operational: build, registry, Product Log, dossier, this checkpoint, the factory state. Then squash per the `wip/` lifecycle and push normally; never force.

**Production verification** (a green deploy isn't enough): the intended commit; live files byte-identical to a fresh build (`sh .claude/scripts/qa.sh 300 prod-parity.mjs`); the real live workflow; console; responsive states; import, export, and persistence where relevant; offline where it applies; the whole-site smoke test; the daily check. **Daily-check failures:** read which check failed, its error, and whether a retry recovered; tell an outside transient from a Labs regression; don't redesign monitoring without evidence of a new blind spot. **Post-ship defects:** fix → test → push → deploy → production-verify → record.

**Lessons to reuse** (not to copy mechanically): Off Book and Captions Up, parser ambiguity; Hidden Data Check, bounded streaming and "incomplete inspection" wording; Transcript Pseudonyms, false-positive replacements; New Classes and Places by Choice, independent optimisation checks; Comp Desk, stale state under fast typing; Deputyship Accounts, overlapping exports and reconciliation; Collection Climate, real file diversity and upper-limit crashes; Holiday Pay Average, the primary regulation beats simplified guidance, official examples slip, and Playwright's `fill` is quadratic for multi-line text (measure with a real paste). Also: the Write and Bash tools rewrite `\u` escapes (placeholders, then the invisible-character scan); save through `useOtherTabs` and `NotSaving`; focus moves at once, never on a delayed frame.
